# REQ-003 详细设计（第一阶段：Mac 端）

版本：v0.2 草案，2026-10-08，**待用户确认**。依据[需求 v0.2](requirement.md)。未通过前不拆任务、不改代码。

## 1. 总体思路

现有 Mac 端的界面层只认 `CodexTask`、`TaskActivity`、`TaskGraph` 这几个通用模型，读取层只有 `LocalCodexSource` 一个来源，由 `TaskStore` 直接持有。本设计**不改动 Codex 的读取路径**，在旁边加一个 Claude Code（下称 cc）来源，两个来源各自出快照，在 `TaskStore` 里合并成一份任务列表；之后的排序、关注、整理、计数、窗口全部沿用现有逻辑。

cc 的状态来自三处，按可靠程度叠加：

| 层 | 来源 | 是否需要 hooks | 能得到什么 |
|---|---|---|---|
| A | 会话记录文件（逐行追加） | 否 | 会话存在、标题、项目、运行、提问等待、完成、中断、出错 |
| B | 运行中会话登记（每进程一个文件） | 否 | 进程是否还在、入口类型（桌面 App／终端等） |
| C | hooks 上报的事件 | 是 | 准确的本轮开始时间、等待权限审批、完成、出错、子代理数量 |

未开 hooks 时只有 A 和 B：权限审批的等待在记录里看不出来，这类会话会显示为运行中，超过 15 分钟没有新活动后按现有规则变为状态未知（R-08、R-16）。

### 2.3 任务标识

cc 任务的 `id` 为 `cc:` 加会话编号。这样不会与 Codex 的编号冲突，关注、排除、自动整理这些按编号保存的设置无需改结构，并且从编号就能看出来源。

## 3. 读取 cc 会话（层 A、B）

### 3.1 发现

- 数据目录：`CLAUDE_CONFIG_DIR` 环境变量，否则 `~/.claude`，设置里可手动指定（R-18）。目录不存在即视为未安装，来源不启动、不报错（R-20）。
- 会话：`projects/<项目目录>/<会话编号>.jsonl`，一个文件一个会话。只取这一层，不进入会话子目录。
- 范围控制：每轮只列目录和文件元数据；已关注的会话、有存活登记的会话、最近 30 天内有改动的会话才打开读取，总数上限 500。文件修改时间只用于决定“要不要读”，不用于任何显示的时间。
- 路径必须位于数据目录之内，否则不读，按“记录位于数据目录之外”处理（与 Codex 一致）。

### 3.2 标题与项目（R-02）

- 标题依次取：会话子目录里的自定义标题文件、记录中的自定义标题行、登记里的会话名；都没有则“未命名会话”。不读取最后一条提问等正文字段来拼标题。
- 项目名取记录里工作目录的最后一段，只在内存中使用。
- 创建时间取第一条带时间的记录，更新时间取最后一条带时间的记录。

### 3.3 归约规则

`ClaudeTranscriptReducer` 只看每行的类型、时间、结束原因、工具名、工具调用编号等元数据，不保留消息正文和工具参数（R-23）。标记为子代理的行、元信息行不参与主会话状态。

| 记录 | 结果 |
|---|---|
| 用户提交的新提问 | 运行中，记本轮开始时间 |
| 助手消息，结束原因为继续调用工具 | 运行中；记下未返回的工具调用编号 |
| 工具结果 | 运行中；清除对应编号 |
| 助手调用提问工具且结果未返回 | 待处理，“等待你的回答” |
| 助手调用退出计划工具且结果未返回 | 待处理，“等待你的确认” |
| 助手消息，结束原因为本轮结束 | 已完成 |
| 用户中断标记 | 已停止 |
| 接口错误标记的助手消息 | 出错，“请回到 Claude Code 查看” |
| 其他类型（快照、队列、标题等） | 不改变状态 |

时间倒序的旧行丢弃；冷启动只读文件尾部 64 KiB，与 Codex 相同。尾部没有读到本轮开始的那条提问时，开始时间为空，界面显示 `--:--`（R-09）；第一阶段不做 cc 的开始时间回查，开 hooks 后由事件补上。

### 3.4 登记的用法

登记文件给出进程号、会话编号、入口类型、状态和更新时间。本阶段只用它做两件事：

1. **进程是否还在**：进程号存在且启动时间与登记一致才算存活。记录显示运行或等待、但进程已不在时，状态改为已停止，“会话已退出”，不继续显示运行。
2. **入口类型**：供点击跳转使用。

登记里的状态字段目前只见到“忙碌”一个取值，其余取值未知，所以**不用它判定等待**；核实结果记入验收文档后，如确有等待取值，再另提设计变更。

### 3.5 子代理（R-06）

子代理不生成独立任务。主会话里未返回的代理工具调用使主会话保持运行中；开 hooks 后，按子代理开始和结束事件计数，在详情里显示“n 个子代理”。子代理触发的权限请求带的是主会话编号，直接让主会话进入待处理。

## 4. hooks 事件（层 C）

### 4.1 注册的事件

只注册下面八个，全部设为后台执行、不等待结果，不返回任何决定，因此不会改变 cc 的行为（R-15）：

| 事件 | 叠加效果 |
|---|---|
| 提交提问 | 运行中，记本轮开始时间 |
| 权限请求 | 待处理，“等待你的审批”，记等待开始时间 |
| 通知（权限提示、需要输入、对话框） | 待处理，按类型区分审批与回答 |
| 通知（空闲提示等其他类型） | 不改变状态 |
| 停止 | 已完成 |
| 停止失败 | 出错 |
| 子代理开始／结束 | 子代理计数加减 |
| 会话结束 | 若仍在运行或等待，改为已停止 |

不注册“每次工具调用前后”的事件，避免每个工具调用都启动一次小程序；等待结束由会话记录里的新行来判断。

### 4.2 叠加规则

记录得出的状态和 hooks 事件都带时间。取两者中较新的一个；“待处理”一旦由事件设立，直到出现更新的记录行或更新的事件才解除。hooks 事件只影响投影出的状态，不改写记录归约器本身，这与现有“桌面回执”对 Codex 的做法一致。事件文件读不到或格式不识别时，退回只用层 A、B。

## 5. hooks 的安装与小程序

### 5.1 小程序 `codex-top-claude-hook`

- 开启 hooks 时，从应用包里复制到 `~/Library/Application Support/Codex Top/bin/`，路径固定，不随应用位置变化；应用升级后首次启动若版本不同则覆盖。
- 从标准输入读 cc 传来的 JSON，只取白名单字段：会话编号、事件名、通知类型、子代理编号、会话结束原因，加当前时间，向 `~/Library/Application Support/Codex Top/claude-events/<会话编号>.jsonl` 追加一行。其余字段（工作目录、记录路径、工具参数、提问内容、最后一条回复）一律丢弃（R-14）。
- 任何错误都静默并以成功状态退出。单个事件文件超过 256 KiB 时只保留后半段。
- cc 设置里的命令写成“小程序存在才执行，否则直接成功”，所以即使删除了本应用，cc 也不会出现报错提示（R-15）。

### 5.2 修改 cc 设置文件（R-11～R-13）

- 目标只有一个：数据目录下的用户级 `settings.json`。不碰项目级和本地级设置。
- 开启流程：设置页开关 → 弹出说明（改哪个文件、加哪八个事件、可随时移除）→ 用户确认 → 备份 → 写入 → 回读校验。
- **保持原内容与顺序**：用一个保留键顺序的 JSON 读写器，原有键、值、数组顺序全部保留，只在 `hooks` 下追加本应用的条目。缩进会统一为两个空格，这是唯一的格式变化。
- 文件不是合法 JSON 时拒绝修改并提示，不尝试修复。读取到写入之间文件若被别人改过，放弃本次写入并提示重试。原子写入，保留原权限。
- 备份放在本应用的 Application Support 目录，保留最近 3 份，不在 cc 目录里留文件。
- 本应用的条目以命令中的固定小程序路径识别。关闭开关时只删这些条目；删完后若某个事件下为空则去掉该事件，`hooks` 为空则去掉该键；文件原本不存在而由本应用创建时，移除后删除该文件。
- 设置页的“已安装”状态每次都从文件回读，不靠本应用自己记的标志。
- 关闭 hooks 或关闭 cc 来源时，清空事件目录。事件文件对应的会话 30 天没有出现则删除。

## 6. 合并进 TaskStore

- **刷新**：一轮刷新里先后取两个来源的快照。任一来源失败只影响它自己的任务，另一个照常显示；警告文字分别说明来源。合并后的任务数组交给现有 `TaskGraph` 和 `MonitoringPolicy`。
- **首次出现 cc 来源**：把当时已存在的全部 cc 会话加入自动关注的基线，并记 `claudeBaselineApplied`。否则升级后，安装本应用以来的所有历史 cc 会话会一次性涌进关注列表。此后新开始的 cc 会话按现有规则自动加入（R-05）。
- **文件监听**：现有监听上限 64 个文件。已关注且在运行或等待的 cc 会话，其记录文件和事件文件加入监听；2 秒轮询兜底不变（R-10）。暂停任务刷新时一并停止。
- **关闭 cc 来源**（R-19）：来源置空，cc 任务从列表消失，关注设置里的 `cc:` 编号保留不删，重新开启后恢复。

## 7. 界面

- **来源标记**（R-03、D-06）：一个小标记视图，CX 为深色方块，CC 为橙色圆角，放在标题之后；任务行、任务选择器、悬停说明都使用。**当前显示的列表里两种来源并存时，所有行都显示标记；只有一种来源时都不显示**。面板按关注列表里的根任务判断，任务选择器按它列出的任务判断，各自独立。cc 来源关闭或未检测到 cc 时列表里只有 Codex，自然不显示，界面与现版本相同（R-19、R-20）。演示模式的合成任务含两种来源，用于验收标记。
- **计数与提醒**（R-04）：`MonitorStatusSummary` 按合并后的任务计算，无需区分来源。
- **文案**（R-21）：归约器给出的详情文字按来源区分；现有写死“Codex”的四处提示改为按任务来源取名。
- **额度**（R-22）：存在 cc 任务时，底栏额度前加“Codex”字样；不显示任何 cc 额度。
- **设置页**：新增“Claude Code”一节，含启用开关、数据目录、hooks 开关及其安装状态和说明。未检测到 cc 时整节显示“未检测到 Claude Code”，开关不可用。
- **演示模式**：加入两条合成的 cc 任务（一条运行、一条待审批），不读真实数据，用于截图和窗口验收。

## 8. 点击跳转（R-17）

按登记里的入口类型分流：

| 情况 | 行为 |
|---|---|
| 桌面 App 的会话 | 激活 Claude 桌面 App。能否直达具体会话待核实；不能时只激活 App。 |
| 终端或 IDE 的会话 | 本阶段不做窗口定位（D-07）。提示“这是终端里的会话，编号已复制”，复制会话编号。 |
| 入口未知或打开失败 | 提示无法定位，复制会话编号。与现有 Codex 跳转失败的处理一致。 |

待处理行沿用现有规则，跳到实际发出请求的任务；cc 没有独立的子任务，所以总是主会话。

## 9. 测试

合成样例放独立临时目录，不读真实 cc 数据：

- 归约器：第 3.3 节每条规则各一例，加乱序、超长行、格式不识别、只有尾部。
- 登记：进程存活、进程已退出、进程号被复用、文件损坏。
- 事件叠加：事件早于或晚于记录、等待后被新记录解除、事件文件缺失。
- 安装器：无文件、空对象、已有他人 hooks、已有本应用旧条目、非法 JSON、写入期间被改动、移除后内容逐字段相等、键顺序保持。
- 来源：未安装、目录外路径、数量上限、标题三级回退。
- 合并：两来源编号不冲突、一方失败、首次基线、关闭后恢复关注。
- 来源标记：全 Codex、全 cc、两者并存三种列表，分别断言不显示、不显示、全部显示；面板与选择器各自判断。
- 既有 Codex 测试全部保持通过，不修改其断言。

## 11. 风险

- 会话记录、登记、hooks 输入都是 cc 的内部格式，随版本可能变化。应对：字段缺失或不识别时显示状态未知，不猜；验收文档记录所验证的 cc 版本。
- 保留键顺序的 JSON 读写器是新写的代码，是本设计里最需要仔细测试的部分；它出错的后果是损坏用户的 cc 设置，所以有备份、回读校验和并发改动检查三道保护。
- 未开 hooks 时，等待权限审批会显示成运行中。这是已知限制，设置页的 hooks 说明里会写明。
