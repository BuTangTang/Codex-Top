# 默认打开最新对话（2026-10-03）

用户要求见[D-44](../REQ-002-局域网多设备监控/requirement.md)：手机保存历史，默认开页直接看最新内容，联网正常且来源电脑可达时3秒内可见；旧历史按需翻阅。它与发送到电脑原记录的三秒门槛分别验收。

## 现场与源码证据

仅回读实体手机目标对话的元数据，没有保存或公开正文、身份和原始设备输出。观察时本地缓存为1080行、609738字节，loaded／hasMore为真，双向游标存在、前向版本7；最新已到10月3日15:07。观察晚于用户15:05截图，因此只证明观察时已入库，不证明打开时最新消息已存在或可见。四个账号槽未找到目标阅读书签。

待发元数据保留五件10月1日／2日旧消息（四件unknown、一件失败），与截图旧时间一致，另有今天已接受但尚未回显的记录。原初始加载先发布最新历史，再恢复旧待发消息；原生插入对普通负编号一律放到最新端，忽略原日期。合成真实分支复现旧消息压到今天消息前，并反转跨天恢复批次。该路径可解释错误落点；整体缓慢还不能据此归为单一原因。

## 本片修复

仅改原Runtime初始type2／max0的pending通知批次及ChatActivity原插入分支：恢复对象显式打标并清除本次刚发送资格；只有本产品、显式恢复、非排期负编号按原日期入列。同秒双负编号以更负较新保持批次与附件顺序。列表预览、真实新发送、普通Telegram、排期、快捷回复、正编号原规则不改。

ID、日期、附件、失败／ACK／unknown保持，不自动重发、不删除待发记录，没有新请求、轮询、弹窗或状态。后台增量、完整旧历史以及游标恢复机制本片未改。

实施方提取正式插入、日期服务行及原跟随分支：初始15例8个行为失败，修后全部通过；追加两例后17／17。独立审查提取正式插入分支13／13；独立实际Runtime恢复六场景先RED后GREEN，覆盖failed／accepted／unknown、已有对象、附件部分回显及空批。主管独立复跑三组共36例通过。独立比对Runtime仅初始恢复六行新增块，其他预览、发送／ACK和队列保持。

实际包构建、签名与安装回读见下方交付记录。真实默认开页、旧阅读位置及三秒可见仍需实际界面计时；桌面工具库存读取本次20秒超时，未改用未授权的ADB界面操作。初始未到尾部时原pending整批拼接、迟到开页事件以及全部异步race未由这36例覆盖。

## 后续同步与存储边界

当前watch有有效旧尾游标时从旧位置顺序追新增；缺尾游标时等连续旧锚找到后才发布。旧v5／v6或失效尾游标的source_discontinuity被拒绝后仍保留原游标，存在重复失败分支。这些是源码可达问题，不是本次现场v7已确认命中。

现有无游标page(older)接口可以直接取得最新一页及该次前向尾游标，无需新RPC。后续沿原TranscriptWindow／TranscriptStore单一所有者保存最新连续段、保留旧段和明确缺口；首个最新页可见不等待旧缺口。只在用户翻到缺口时补页，较旧分页不覆盖最新前向游标。来源身份稳定；现有原生正整数ID同时用于排序和分页，不能靠任意预留数字空洞冒充连续历史，接通缺口时须同步原生窗口及阅读锚点。当前该分段方案尚未实施。

源码检查：Direct Sessions正文page／readAfter由电脑原rollout提供；服务端delta仅ephemeral转发，关联保存元数据。普通persisted会话及显式takeover/import另有SessionMessage持久记录。因此本次direct路径与“手机缓存、服务器转发”方向相符，不能把路由Redis TTL误作已实现的短期离线队列；没有读取远端数据库／配置，未确认现场是否有旧导入全文，未删除任何服务器记录。
