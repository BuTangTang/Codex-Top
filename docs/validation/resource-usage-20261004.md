# 2026-10-04 桌面资源优化

## 目标与口径

用户已确认：在不降低消息同步速度、不影响账号和聊天记录、不增加操作负担的前提下，降低 Codex Top 的 CPU、内存和安装体积。按正式包基线、热点修改、独立复核、测试、实际窗口和复采分别记录，不用延长轮询间隔换取低占用。

范围是正式 Codex Top GUI、随包连接 daemon 及其 caffeinate 子进程。两份既有源码 QA daemon 不计入，也未停用。原始进程／堆栈记录留在 Git 忽略目录，公开记录不含对话正文、账号标识或完整本机路径。

## 第一片：build 80 → 81

### 改动

- 增量文件读取只取 inode、尺寸和精确修改时间，使用 `lstat` 保留原 Foundation 不跟随末级符号链接的行为，避免正常热路径读取扩展属性。保留截断、替换、等长重写和计时回查前后校验；失败仍报告原 Foundation 文件错误。
- TaskStore 相同任务、额度、警告和偏好不重复发布，无内容变化不重建任务图或触发窗口重排。每轮仍执行过期规则，保留两秒刷新、200ms 文件事件合并、刷新按钮 busy、完成状态和错误恢复。
- canonical 连接打包器仅删除已核实 ONNX 1.21.0 中非目标操作系统的文件。Mac 保留两个 Darwin 架构及完整动态库，不关闭模型功能或改变同步策略。未知版本／布局保留，链接在删除前拒绝。

### 基线与实测

正式 build 80、圆环显示两个运行任务。每次 `top` 采21帧，去掉首帧，20个有效样本；CPU为单核百分比，MEM使用相同工具口径。共享电脑仍有其他工作，短窗结果不代表全天或所有任务规模。

| --- | --- | --- |
| GUI 平均 CPU | 10.425%（另一轮10.060%） | 6.860%（复采7.185%） |
| daemon 平均 CPU | 0.205% | 0.250% |
| GUI MEM | 113 MiB | 79 MiB |
| daemon MEM | 231 MiB | 188 MiB |
| 安装目录 `du -sk` | 1,353,372 KiB | 1,214,740 KiB |

安装目录减少138,632 KiB，约135.4 MiB。实际裁掉13个非Mac文件、149,936,608原始字节；保留993个ONNX文件逐一SHA相同。安装目录还包含签名等内容，不能把两种统计口径混用。

内存前后不是同进程年龄：旧进程已运行约17小时，新进程刚重启。**这组内存差不能作为优化收益或泄漏证据**；内存延迟加载另行验证。第二轮同场景CPU复采仍较低，后台平均0.160%、GUI79MiB／后台188MiB。

### 验证

- 两项TaskStore合成回归先失败后通过：相同刷新原有7次内容发布及1次重排，修正后均0；busy仍先真后假。新完成记录、丢源、相同失败及恢复仍沿真实数据源路径验证。
- 新8项元数据边界及原增量／计时／长等待专项24项通过；全Swift216项、release构建通过。
- 固定64个合成文件，每轮25,600次、五轮交替顺序的元数据微基准中位数1404.94ms → 67.26ms。仅为该操作的证据，不代表应用CPU比例。
- canonical裁剪专项19项先失败后通过，整个componentArtifacts42项及包类型检查通过。独立复核发现测试Windows路径键及夹具许可缺失，已修正并复跑19项。
- Codex独立复核、Cursor/Grok实际只读复核均无当前生产阻断；主管回读源码和边界。仍有busy发布，不称完全消除周期界面更新。
- 正式连接1.0.0+codextop.81、App构建及严格深签名通过，已安装。账号和机器身份保持，真实窗口圆环、展开任务列表、收回圆环通过；只有一份正式GUI／daemon。
- 构建前工作区CLI dist与build80包内318个文件逐一一致；构建期间原CLI／协议源码保持。未修改手机或原Codex数据。
- 新包五秒堆栈复采未再出现本次定位的`getxattr`／扩展属性读取；该短采样不等于所有场景成本为零。安装后只保留81当前与80回退，退役79前检查使用情况，保留包执行文件SHA再次核对通过。
- canonical打包源提交`747a70ae9`，已推送自有移动仓库`codex/native-qfl-20261001`的`3b6a49e53`，保留原远端workflow。夹具按原文件字节保留，包括上游一处行尾空格及完整许可，不改哈希以求格式检查通过。

### 已知边界与下一步

ONNX native在Node与Bun中均能实际加载。完整Transformers ESM在旧80和新81中均因既有`onnxruntime-common`嵌套布局缺口失败；没有下载或运行模型，不能把native通过当作完整模型功能通过。这是单独的既有依赖闭包问题，本片没有全局提升依赖或临时绕过。

外接屏、实体手机收发与最新页三秒仍未在本片验收；本片没有变更其传输、轮询或历史策略。以上为第一片时的边界，后续内存对照如下。

## 第二片：build 81 → 82

### 改动与保护边界

命令注册表原26个内建处理器改为命令命中时加载，使用字面量动态导入，四组别名仍指向同一包装器；provider注册、参数、错误传播不变。凭据检查不再提前加载终端UI，只有实际进入交互选择时才导入AuthSelector、React和Ink，原认证请求、取消、raw mode与清理保持。

没有延长刷新、消息轮询或超时，没有修改历史、消息、账号数据和手机包，没有添加GC定时器或用户提示。Swift源码沿用第一片，216项全测与release证据保持，正式App构建再次执行release。

### 对照与验收

- 加载边界先验证原代码会提前初始化Ink，再分别覆盖认证与注册表两个入口；新回归与相邻9文件43项、CLI类型检查通过，两路Codex独立复核无阻断。
- 隔离源图使用合成HOME、网络／进程边界守卫；Node与Bun编译产物共六点实际运行命令、真实Ink选择与取消，边界违规0。Bun真实按需加载得到验证，但模块探针中约17MiB的注册表差值**不是**正式daemon收益；完整daemon代码导入阶段差值只有约5.6MiB。
- 正式82实际执行`--version`、`--help`、`plugins list --json`、`status --yes`（预期只读错误）及`auth --help`通过。使用非TTY、清洁环境、临时HOME并显式关闭更新检查、runtime替换和自动启动daemon；未使用会跳过命令分派的integrity-probe标记。
- canonical连接／正式App构建、严格深签名通过；构建期间6,321份CLI／协议源文件SHA保持。覆盖安装后原账号、机器身份和单一daemon保持，实际打包窗口圆环、展开任务面板、收回通过。重绑定Computer Use会话解决更新后旧元素失效，不把工具绑定问题算作产品故障。

为避免17小时旧进程与刚重启进程的混淆，本片把旧81也用原生命周期重新启动。同一正式账号，每次先等待30秒，发一次原路由只读STATUS（含当前目标），再在约一分钟启动年龄采21帧`top`，去首帧，取20样本。服务恢复后身份一致；没有发送新消息、重试旧消息或写原Codex文件。

采用相同启动年龄的第一和第三行比较：本次短窗内存中位数少4MiB，约2%，尚不能外推长期稳定收益。第一和第二行年龄不同，不把13MiB差值作为结论。后台CPU在短窗内波动，**不宣称这片降低后台CPU**。原路由状态读取未见变慢，但它不等同于手机发送或完整历史同步测速。此时运行任务数已从第一片的2变为1，不用82的GUI读数继续计算第一片的CPU改善比例。

### 范围结论

本轮完成可复测基线、两个热点修正、独立复核和正式包验证，保留原同步频率与账号数据。主要收益来自GUI热路径和安装体积；本次同启动年龄短窗观察到约4MiB内存差值，不宣传长期稳定收益、大幅节省或泄漏已解决。

采样时仅内置屏可用，外接屏未验；旧手机三秒、发送、图片后文字、目标写入等缺口均不因这次资源优化而关闭。完整Transformers ESM的既有依赖缺口同样保留。未来若继续压缩常驻内存，应先测长时间持有对象与实际负载，不能仅按导入探针或重启差值继续删功能。

收尾保留82当前和81回退，退役80前核对进程、打开句柄与构建状态，保留包签名及GUI／CLI的SHA再次通过。内存源提交`3d888a73d`，自有移动仓库发布提交`e7cdb0dfb`逐文件blob一致，保持原远端workflow。
