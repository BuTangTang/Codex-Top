# 待处理记录核对与来源任务跳转

初验：2026-09-13；复查：2026-09-14。应用：v0.1.0 build 3。不同日期的证据分别记录。

## 已确认的现象

用户反馈已提交问题卡片，但监控仍显示待处理。只读核对期间，该任务尚没有与最后提问对应的用户回复。随后相同提问 ID 的结构化回复记录到达，安装新版前仍运行的 build 2 已自行恢复为运行中。此过程只证明后来读到了回复且旧实例能够清除等待，不能确定从点击提交到状态更新的延迟发生在哪一环节；也没有证据量化其耗时。原始日志、任务标题、答案、截图和本机路径均不进入公开材料。

## 本次代码修正

- 聚合任务行可能展示子孙任务的等待状态，旧点击逻辑却始终打开主任务。现在等待状态、计时和导航使用同一来源选择；主任务自身等待时保留主任务，非待处理行沿用原跳转。
- 跳转失败时复制实际目标任务 ID，避免复制错误的主任务 ID。
- 待处理行的悬停说明展示进入待处理和最近活动的时间、缺失时间和答复同步边界；不增加时间菜单或对话正文缓存。
- 当前安装的 Codex 外部协议解析只返回任务标识及受支持的 review 等入口，未提供单条问题或回复位置参数。用户要求的精确问题定位未实现，不以任务跳转代替该验收结论。

## 2026-09-14 长等待复查

用户补充“等待一段时间再回复容易出现”。只读核对安装版本、程序摘要和进程，确认仍是上述 build 3，唯一真实实例，未在本次诊断中重启。此次记录里，截图对应的提问收到回复后约 9 秒出现另一条新提问；新提问也收到对应回复后，真实圆环显示 0 个需要处理，展开面板中目标任务显示运行中。另有一条等待约 109 分钟的问题也存在匹配回复。提问标识用于本地核对，不写入公开材料。

新增 `LongWaitReplyTests` 的 3 项回归使用合成记录和独立临时数据库：

| 场景 | 结果 |
| --- | --- |
| 模拟等待 20 分钟、2 小时、24 小时；期间文件和数据库时间戳不变 | waiting 保留；追加回复后首个快照恢复运行，开始时间和轮次保留、等待时间清空 |
| 结构化卡片回复、`user_message`、`item_completed(UserMessage)` | 三种现有回复入口均恢复 |
| 两小时后追加超过 4 MiB 的工具输出及回复 | 追赶期间显示同步未知；下一快照读到回复即恢复，旧等待不残留 |
| 旧回复及 9 秒后的新问题在同次快照到达 | 等待时间锚定新问题；新回复解除等待，后续完成记录正常结束 |

`swift test` 共 117 项通过，`swift build -c release` 通过。本轮没有产品代码变更，也未重新安装应用。上述等待时长通过事件和观察时间模拟，并非真实持续休眠或等待一天；不能替代 App Nap、系统唤醒或用户提交瞬间到日志可读之间的现场验收。

当前未复现“仅因等待时间长就漏清回复”，也未发现按等待时长拒收回复的逻辑。用户反馈的间歇性问题尚未完整定位，不能标为已修复；后续应在现象仍存在时对齐同一提问、对应回复的可读时刻及真实监控状态。不会用等待超时来推断已经回答。单条问题/回复的精确导航限制继续保留。
