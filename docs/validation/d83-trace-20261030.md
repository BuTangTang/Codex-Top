## 2. 已证实的问题

### B1 缺陷：同一轮内第二个审批沿用第一个审批的摘要

**静态代码可证明的部分**（ter `b28e40f`，只读核对）：

1. `SessionStatus.candidateSnapshot`：状态为 `needs_input` 时逐个读取请求；`kind` 为 `user_action_request` 的请求把 `requestId` 加进 `questionIds`，`kind` 为 `permission_request` 的只记 `approval = true`，编号不进入任何集合。
2. `CodexRuntime.pendingIdentity`：标识 = `turnId` + 排序后的 `questionIds`。因此只有审批的两个状态，只要 `turnId` 相同，标识就相同。
3. `CodexRuntime.rememberPending`：打开会话读到审批后，以当时的标识存下“批准：第一条命令”。`pendingSummaries` 只在这里写入、只在账号重置时整体清空，状态离开待处理时不清。
4. `CodexRuntime.pinnedPendingText`：类别为待处理且标识相同就返回已存摘要，不再核对请求编号。

由 1～4 可推出：同一 `turnId` 下先后出现两个审批，而用户只在第一个时打开过会话，置顶区会对第二个审批显示第一个审批的命令。这是逻辑推论，不依赖运行。

**静态无法确认、需运行才能证实的前提**：Codex 在同一轮里是否确实会先后发出两个审批请求、且两者 `turnId` 相同。若真实 Codex 每个审批都换新的 `turnId`，此缺陷在真实使用中不会出现，但代码逻辑仍依赖这个未约定的前提。

**本轮未执行的复现步骤**（供实施时执行，执行后再把结论改为“已复现”或“未能复现”）：

1. 在电脑上让一个 Codex 会话在同一轮里依次请求两个需要批准的命令。
2. 第一个请求出现后，在手机上点进会话看到审批，返回列表，记下置顶区第二行（期望为“批准：命令1”）。
3. 在电脑上批准第一个，等第二个请求出现。
4. 不点进会话，看置顶区。若仍为“批准：命令1”即为复现；期望显示“待批准，点开查看”或“批准：命令2”。

也可以不依赖真实 Codex，用 JVM 测试复现：构造同 `turnId`、不同审批 `requestId` 的两个状态快照，断言第二个快照下摘要失效。该测试本轮未编写、未运行。

**修正方向（任务 T12，下次实施优先做）**：标识里加入审批的 `requestId`，并在状态离开待处理时清掉该会话的摘要。不改变任何界面规则，属于按已通过设计修正。

### R3 追踪：列表冻结与解冻（ter `b28e40f`，只读）

**冻结期间被跳过的刷新**：

- `DialogsActivity.didReceivedNotification` 收到 `dialogsNeedReload` 时，若 `dialogsListFrozen` 为真直接返回（约第10649行）。这是 Telegram 原逻辑，对所有会话都一样。
- 收到 `updateInterfaces` 时先 `updateVisibleRows(mask)` 重画可见行（状态图标、小标签会更新），D-83 新增的 `arrangementChanged()` 检查带 `!dialogsListFrozen` 条件（约第10725行），冻结期间不执行。

**解冻时的补排**：

- 单参数 `setDialogsListFrozen(false)` 等于 `setDialogsListFrozen(false, true)`（约第11094行）。带通知的解冻会调用 `viewPages[0].dialogsAdapter.notifyDataSetChanged()`（约第11075～11092行）。
- `DialogsAdapter.notifyDataSetChanged()` 被重写为先 `updateItemList()` 再通知（约第661行）。在 Codex 根页，`updateItemList()` 走 `codexArranged()` 分支，调用 `CodexRuntime.arrangedRows()`，用当时的会话和状态重新分组，并更新 `arrangedSignature`。因此冻结期间错过的状态变化在解冻时会体现。
- 冻结点及其解冻：滑动操作（约第2578行冻结，第2591、2599行延时300毫秒解冻）；过渡动画（第5550、5568行）；第7669行冻结、第7725、7786行解冻；标记已读、删除等操作经 `checkAnimationFinished()` 在300毫秒后 `setDialogsListFrozen(false)`（第9041～9052行）；第10303、10327行同理。以上解冻都带通知。
- 例外一：第9699行 `setDialogsListFrozen(false, false)` 不通知。它只在 `filter != null` 且为“仅未读”筛选时执行，`filter` 只在 `dialogsType` 为7或8时取得；`codexArranged()` 要求 `dialogsType == DIALOGS_TYPE_DEFAULT`（0），所以这条路径不会出现在 Codex 分组页。
- 例外二：第2609、2611行在归档撤销的同一个回调里直接置位又复位，中间没有让出界面线程，不会漏掉通知。

**结论**：静态上看，Codex 分组页的所有冻结都以带通知的解冻结束，解冻会整表重建分组，R3 不构成缺陷。剩余的不确定只有两点，属于可选的运行核对：解冻时用整表刷新而不是差异动画，行会直接跳到新位置；`setDialogsListFrozen` 只通知 `viewPages[0]`，Codex 根页没有筛选标签页时这一点无影响，但未在运行中确认第二页不可见。可选核对办法：在300毫秒冻结窗口内（如滑动后立即）让一个会话从运行变为完成，等解冻后看它是否移入“已结束”。

### R4 核对：排序键与同值时的后备顺序

**已批准文档对排序的约束**：

- 需求 D-83 只写“项目组按最近活动排序，组内会话按时间排序”“按时间模式：一个列表，最近活动在最上面”，没有规定时间精度，也没有允许同一秒内顺序任意。
- 设计第3节规定分组模型的输入含“最近活动毫秒、远端 ID（时间相同时稳定排序用）”，并写“组内会话按时间排序，时间相同时按远端 ID”。即远端编号只用于毫秒值相同的情况。

**代码现状**（ter `b28e40f`，只读）：

- 数据源：候选带毫秒时间 `updatedAtMs`。`publishDialogs` 用它给原 `dialogs` 列表排序（同值按远端编号），同时把 `updatedAtMs / 1000` 写进 `dialog.last_message_date`（`CodexRuntime` 约第4362行），毫秒部分被舍去。
- 新比较器：`arrangementEntries` 传给分组模型的时间是 `dialog.last_message_date * 1000L`，所以只有秒精度。`BY_TIME` 先比这个值，相同时比 `remoteId`；项目之间 `BY_ACTIVITY` 比组内最大值，相同时比分组键；电脑之间相同时比电脑编号。`arrangementEntries` 跳过没有远端编号的会话，后备键不为空。
- 后果：同一秒内更新的两个会话，在组内、置顶区和按时间模式里按远端编号排，而不是按实际先后；同一秒内更新的两个项目也按分组键排。顺序固定，不会来回跳，但可能与实际先后相反。

**分类**：设计明确输入为毫秒，同秒内按远端编号排只是秒精度造成的结果，不是文档允许的顺序，因此**不排除**，归为实现与已通过设计不一致，影响低（只在同一秒内多个会话更新时出现）。修正方向是把候选的毫秒时间传给分组模型，属于按已通过设计修正，不新增要求；修正前可用 JVM 测试复现：两条会话同秒不同毫秒、远端编号顺序与时间顺序相反，断言较新的一条在前。该测试本轮未编写、未运行。

### 7.4 电脑端拒绝原因与待条件

- 12.10.58 起手机日志稳定出现 `claude_candidates` 失败，类型为电脑端明确拒绝（`RpcFailedException`）；Codex 列表同时正常。
