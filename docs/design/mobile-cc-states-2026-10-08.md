# 接入 Claude Code 后的状态呈现

设计预览，尚未实现，未修改或安装 App。来自 2026-10-08 与用户的界面讨论：若以后接入 Claude Code（下称 cc），手机端和 Mac 端如何在同一份列表里呈现两种来源，并把运行中、出错、未知等状态全部照顾到。示意图只在对话中给出，使用示例数据，未存入仓库。

## 选定方向（2026-10-08）

之后出了三个版本：按状态分组、按电脑分区、头像身份，每版五块屏，使用同一批示例数据（三台电脑、两种工具、十一个会话、九种状态）。用户要求不同电脑、不同工具都能看清，选定**按电脑分区**；又指出行太密容易误触，改为每行不低于48dp、行间加分隔线、待办置顶、已结束与离线电脑折叠后确认。选定版本的图片与要求已写入[需求 D-45](../REQ-002-局域网多设备监控/requirement.md#多来源界面增量需求-d-45草案2026-10-08未实施)，以需求为准；下面“取舍”和“各页面”是选定前的初稿，其中列表分组方式已被 D-45 取代，状态表和规则继续有效。

未选的两版：按状态分组把同一台电脑的任务拆进四个组，答不了“这台机器在干什么”；头像身份改动最小，但电脑靠角标颜色区分，超过三台不好认。

## 取舍

两种来源混排在一份列表里，不分页面；用户关心的是哪个任务在等自己，其次才是由谁执行。列表按状态分组，组的顺序沿用 Mac 端 `TaskPhase.priority`：待处理、出错、运行中、未知、未运行、已停止、已完成。

## 状态表

取值与 `Sources/CodexTopCore/Models.swift` 的 `TaskPhase` 七项逐一对应，另加两种手机端已有的显示情形（同步中、电脑离线），二者都归入“无法确认”。

| 状态 | 对应取值 | 图标与颜色 | 列表分组 | 行样式 | 时间列 |
|---|---|---|---|---|---|
| 待处理（回答／审批） | waiting | 琥珀 `!` | 需要你处理，最前 | 双行，琥珀底 | 固定等待时长，缺失 `--:--` |
| 出错 | failed | 红叉 | 需要你处理，待处理之后 | 双行，红底 | 发生时间 |
| 运行中 | running | 蓝弧旋转 | 运行中 | 双行，标题保持主文字色 | 本轮计时，缺失 `--:--` |
| 状态未知 | unknown（含 15 分钟无活动的过期运行） | 灰问号 | 无法确认 | 双行，灰标题 | 最后活动时间 |
| 同步中 | 记录未读完 | 灰刷新 | 无法确认 | 双行 | 无 |
| 电脑离线 | 来源不可达 | 灰断网 | 无法确认 | 双行，写明“上次显示…” | 最后活动时间 |
| 已完成 | completed | 绿勾 | 已结束 | 单行，不加粗 | 结束时间 |
| 已停止（含取消） | stopped | 灰方块 | 已结束 | 单行，灰 | 结束时间 |
| 未运行 | idle | 空心圈 | 已结束 | 单行，灰 | 更新时间 |

## 规则

- 状态同时用图标、颜色和文字表达，不只靠颜色。
- 蓝色只给运行指示；运行中的标题不变蓝，沿用 Mac 端约定。
- 缺失、过期和无法判断的状态单独成组，不混进运行或完成。
- 时间缺失一律显示 `--:--`，不用创建时间、文件时间或当前时间估算。
- 系统开启“减少动态效果”时，旋转改为静态提示。
- 来源角标（Codex／Claude Code）放在标题之后，行首位置留给状态图标。
- 额度按来源分卡展示，各带采集时间；两边周期不同（Codex 7 天，cc 5 小时与 7 天），不合并成一个进度条。读取不到时显示“暂无法读取”，不留空也不估算。

## 各页面

- **会话列表**：顶部来源筛选（全部／Codex／Claude），下面四组：需要你处理、运行中、无法确认、已结束。
- **聊天页**：标题下方一条状态条，与列表同一套状态。运行中显示计时与“停止”，待审批显示“查看”，出错显示“重试”，电脑离线说明消息暂时发不出；已完成时不显示状态条。cc 的权限请求以卡片呈现，列出具体命令，提供允许、拒绝、本会话始终允许。
- **我的**：两张额度卡，其余不变。
- **电脑**：结构不变，每台电脑卡片加一行各来源会话数。
- **Mac 面板**：沿用现有配色与布局，任务行加来源角标，底栏并排两套额度。

## 未核实的前提

以下都画进了示意图，但能否实现尚未验证：

- cc 的本地记录是消息流，没有 Codex 那样明确的轮次开始、结束和请求输入事件；“等待审批”在记录里基本看不出，需要 cc 的 hooks 或电脑端连接组件上报。hooks 要写 cc 的配置，与本项目对 Codex 数据只读的约定如何对应，待用户决定。
- 手机端的允许／拒绝、停止、重试需要把操作回传给 cc；连接组件（Happier）是否支持未核实，其源码不在本仓库。
- cc 额度是否有可读来源未核实。
- 子代理数量的归并方式需重写。
- Mac 端目前没有数据源抽象，`TaskStore` 直接持有 `LocalCodexSource`，跳转链接与应用标识写死为 Codex。

若先做只读监控，第一阶段预计只能可靠给出运行中、已完成和状态未知三种，待审批与额度落在“无法确认”或 `--:--`。

## 命名

接入 cc 后，“Codex Top”的名称和“Codex 额度”“请回到 Codex 查看”等文案需要按来源区分；是否改名由用户决定。
